# 学习与校招讲解

## 先能讲清一条真实请求

以“移动任务”为例：Vue 看板发 POST → Gin 鉴权中间件读取 Cookie → Handler 校验任务 ID/状态/version → Service 定位所属项目与团队、校验当前成员及归档 → 同一事务按团队/项目/任务锁序读取 → Repository 重排、条件更新版本、递增项目 revision → 写操作日志 → 提交并返回 DTO。

建议按顺序阅读：cmd/server/main.go、router/task_routes.go、middleware/auth.go、handler/task_handler.go、service/task_service.go、repository/task_repository.go、dto/task.go，再看对应 integration/task_test.go。

## 重要取舍

单体分层适合当前学习与演示规模；一个数据库事务就能覆盖业务和日志，无需处理分布式事务。Redis 只管理会话和限流，列表/统计直接查 MySQL，避免缓存一致性问题。团队成员共享全部项目，减少两套权限模型的冲突。

任务 version 保护旧编辑不覆盖新结果，行锁保护排序和成员变更边界；看板 revision 是分页快照标记，不是另一个任务版本。状态统计在同一 REPEATABLE READ 事务中读取，防止同一响应里的总数与分组不一致。

平台 admin 与团队 owner 是两套角色；平台查看摘要/禁用用户不代表能编辑任意团队任务。禁止自我禁用，交叉禁用在锁内重新校验操作者，避免双方都成功。启用用户递增会话版本，因此历史会话不复活。
